# 프로젝트 작업 지시 정리

2026-09-29까지 이 대화에서 정한 사용자 요구를 주제별로 정리한 문서입니다. 대화 원문이나 모든 구현의 완료를 증명하는 목록은 아닙니다. 정책 세부 사항은 `policies/REVIEW_GUIDE.md`, 아직 구현하지 않은 위클리 변경은 `docs/WEEKLY_PENDING.md`를 우선 참고합니다.

## 1. 수집 범위·비용 통제

- 수동 강제 집계를 사용자가 지시하지 않는 한, 성공 이력이 있는 건을 자동 재수집하지 않는다.
- 정기 집계는 미수집·조회 실패 건만 대상으로 한다. 검토 필요, 판단 보류, 환불 확인 중이라는 이유는 재수집 사유가 아니다.
- 정책 재검토는 저장 자료를 우선 사용한다. 자료가 부족하면 부족한 필드·원문·시점을 설명하고 새 수집 범위는 별도 지시를 받는다.
- 수집 전에 대상 날짜·확인된 건수·아직 알 수 없는 건수를 구분해 보고한다. 대상 보고 후에는 이미 승인된 범위의 실행을 불필요하게 다시 묻지 않는다.
- 인증 필요, 발송일 불일치, 중단 등 해결이 필요한 상황은 즉시 알려야 한다. 가만히 대기하면서 진행 중인 것처럼 표현하지 않는다.
- 발송일 불일치에 대한 사용자의 개별 날짜 인정은 해당 사례에만 적용하고, 일반적인 추측 규칙으로 확대하지 않는다.

## 2. 알림

- 오전 정기 실행은 사전 대상 보고 한 번, 전체 흐름 종료 알림 한 번으로 정리한다.
- 하루 종일 5분 간격으로 변화 없음이나 진행 상황을 알리지 않는다.
- 일별·모니터링·자동취소가 같은 흐름이면 종료 결과를 합쳐 알린다.
- 실행 중에는 완료라고 말하지 않는다. 실패·중단·인증 필요는 원인과 필요한 조치로 알린다.
- 실제 알린 실행 ID만 알림 상태 파일에 기록하고 중복 알림을 방지한다.

## 3. 데일리·위클리

- 메일 1건이 집계 1건이다. 같은 주문이 다른 날짜에 발송됐다면 해당 날짜의 메일 집계에 포함한다.
- 테스트 계정 sh7000은 실제 집계에서 제외한다.
- 수집 당시 상태 및 실제 실행 시작·종료 시각을 보관한다. 수동 결과가 최초 일별 기준값을 덮어쓰지 않는다.
- 주간 범위는 금요일~목요일이다.
- **최신 요청:** 금요일에 지난 금~목 대상의 현재 상태를 다시 조회하는 독립 주간 집계. 미구현이므로 기존 일별 합산을 새 방식처럼 설명하지 않는다.

## 4. 모니터링 판단

- 1011 취소 요청 발송 당시의 원인과 고객 의사를 기준으로 원인→응답→후속 처리의 전체 흐름을 읽는다.
- 주문번호뿐 아니라 저장된 Buyer ID 조회, 동일 카트, 주문 연결을 확인한다. 다른 주문의 취소 의사를 무조건 확대하지 않는다.
- 현재 고객 의사나 나중 답변만으로 최초 고객 취소 원인이 소급해서 사라졌다고 판단하지 않는다.
- 개인 변심·잘못된 주문·수정 후 재주문, 처방전·문진·구매 제한, 주소·이름 오류, 사전 품절 고지, 셀러 전언, 취소 완료 후 빠른 고객 승인 등 누적 예외를 함께 적용한다.
- 단어만 보고 분류하지 않는다. 작성자, 대상 주문, 발송 전후 시각, 질문·가정·부정·철회·후속 정정을 구분한다.
- 실제로 읽지 않은 Buyer ID 검색이나 원문을 확인했다고 주장하지 않는다.

## 5. 사용자 판단과 최종 분류

- 사용자 확정 판단과 코멘트는 별도 삭제 지시 전까지 계속 보존한다. 재수집·재평가·서버 재시작으로 삭제하거나 덮어쓰지 않는다.
- 사용자 악용 맞음은 AI와 무관하게 최종 악용이다.
- 사용자 악용 아님은 AI 악용보다 우선하며, 현재 UI에서는 고객사정에 분류한다.
- 별도 사용자 판단이 없으면 AI 악용 결과를 최종 악용에 적용한다. 보류 등 세부 우선순위는 정책 원문을 따른다.
- AI 재평가를 사용자 확정 판단으로 저장하지 않는다.
- 사용자 코멘트는 유사 근거의 다음 판단에 참고하되, 개별 예외를 무조건 모든 주문에 복사하지 않는다.
- 저장한 판단 결과는 모니터링 내부의 ‘내 판단 기록’에 모아 본다.

## 6. 판단 확신도

- 1~5단계로 표시하고 근거와 추가 확인 필요 사항을 제시한다. 정답 확률이나 악용 확률이 아니다.
- 셀러가 고객에게 먼저 취소 요청을 받았다고 명확히 설명하지만 ADMIN에서 구매자 원문 확인이 어려운 경우 고객사정·확신도 3으로 처리한다.
- 취소 처리 완료 안내 + 24시간 내 고객 본인의 승인 + 저장 범위 내 이의 없음 예외 역시 추정에 해당하므로 확신도 3이다.
- 명확한 선행 셀러 귀책·상충·사용자 판단을 낮은 확신도의 추정 규칙이 덮어쓰지 않는다.

## 7. 자동취소

- 최종 상태를 자동취소, 고객 승인, 고객 거절, 셀러캔슬, 요청 대기, 판별 불가로 구분해 필터링한다.
- 요청 대기처럼 보이는 건도 저장된 REFUSE 이력이 있으면 거절 시각·이력을 확인하고 해당 요청의 고객 거절로 집계한다.
- `cancel:Seller Cancel Request`에 대한 셀러캔슬 분류는 최신 사용자 정책과 요청 주기·후속 이력을 함께 따른다.
- 고객 거절 이후 Information의 Shipping status를 별도 표시한다. 配送中/配送完了/発注キャンセル 등 원문 상태와 조회 시각을 구분한다.
- 거절 후 배송 상태는 별도 필터와 열로 표시한다. 배송 상태 조회 시각을 실제 배송 사건 발생 시각처럼 표기하지 않는다.
- 같은 주문의 현재 모니터링 최종 악용 여부를 Y/N/미확인으로 연결하며, 과거 자동취소 조회 당시 판단인 것처럼 표현하지 않는다.
- 요청일은 저장된 기간의 시작·종료일로 검색할 수 있어야 한다. 검색·필터·과거 이력 열기는 새 수집을 실행하지 않는다.

## 8. 셀러관리

- 별도 셀러관리 메뉴에서 최종 악용 셀러와 누적 고유 주문 수, 주문별 상세 근거, 사용자 판단·코멘트, 발신 기록을 관리한다.
- 동일 주문의 중복 날짜 이력은 누적 횟수를 중복 증가시키지 않는다.
- 날짜 범위, 셀러 ID, 누적 1회/2회/3회/4회 이상 검색 및 전체 선택(모든 검색 결과 페이지)을 지원한다.
- 셀러의 자세한 주문 건·대화 근거와 다운로드를 제공한다.
- sh7000은 사용자가 시험할 수 있게 테스트 계정으로 표시하되 실제 악용 집계에서 제외한다.
- 셀러관리 메뉴는 기본 메뉴에 유지하고, 좁은 화면에서도 스크롤 중 접근할 수 있게 한다.

## 9. 메시지 템플릿

- 사용자가 템플릿 이름·발신 제목·본문을 생성·편집·관리한다.
- 대상 선택 후 템플릿을 선택한다. 준비 당시 제목·본문을 보관해 나중 템플릿 편집이 과거 발신 기록을 바꾸지 않게 한다.
- 셀러별 1회 발송하며 대표 주문을 연결하고 전체 대상 주문번호를 본문에 포함한다.
- 대상·제목·본문·실행 시각·결과·실패 또는 미확인 원인을 기록한다.

## 10. 어드민 발신 절차·직접 발신

- Message to Seller에서 Cust ID=대상 Seller ID, Order No=대표 주문을 입력·확인한다.
- Seller 수신자 1명을 확인하고 Subject의 Input Title, Urgent, Also Send Mail을 체크한다.
- 제목과 본문은 사용자가 선택한 템플릿 및 대상 주문 목록으로 채운다.
- Category는 キャンセル/払い戻し(06), Warning은 N으로 유지한다.
- 사용자가 직접 대상과 템플릿을 선택하여 발신을 확인한 경우에만 Send까지 실행한다.
- 초기에는 sh7000 테스트만 허용했으나 이후 사용자가 직접 발신할 수 있도록 제한 해제를 지시했다. 이 변경은 AI의 임의 추가 발송 승인이 아니다.
- 서버 시작·집계·새로고침·준비본 저장은 메시지를 발송하지 않는다.
- 불명확한 결과를 성공이라 하지 않으며 자동 재발신하지 않는다. 어드민 발신 확인과 실제 이메일 배달 확인은 다르다.

## 11. UI·검색·내보내기

- 한국어 메뉴는 영어 중복 표기를 제거한다. 일본어는 일본어로 표시하고 Meiryo UI를 사용한다.
- 모니터링과 자동취소는 저장된 날짜 범위로 조회하고 상태별 필터와 다운로드를 제공한다.
- 모든 표시 주문번호 앞에는 글자 ‘복사’ 대신 복사 아이콘을 둔다. 접근성 이름과 복사 성공 피드백은 유지한다.
- 사용자 판단 입력은 로컬 대시보드에서 가능해야 한다. 사내 공유 읽기 전용 화면과 구분한다.
- UI 예시를 먼저 요청받은 경우 실제 변경 전에 예시를 제시한다.

## 12. 공유·보관

- 로컬 대시보드와 Google Drive 공유본은 별개다. 로컬 변경만으로 Drive가 업데이트됐다고 말하지 않는다.
- 공유본은 사용자가 지정한 사내 폴더의 승인된 기존 공유 범위에 업데이트한다.
- 로컬 PC 주소는 다른 사무실에서 접근되지 않을 수 있으므로 접속 가능한 공유 방식을 구분한다.
- Drive 공유본의 읽기 전용 제한, 최신 저장 시각, 스냅샷과 실시간 연결 여부를 정확히 설명한다.
- GitHub 보관 대상은 작업 지시·정책·자동화 프롬프트 정리본이며, 전체 원문 대화 포함 여부는 별도 결정한다.

## 13. 변경·검증 절차

- 판단 변경 전에 누적 정책을 읽고 기존 정책을 회귀 검증한다.
- 정책 변경은 문서·한국어/일본어 UI·판별 코드·긍정/반례 테스트를 함께 갱신한다.
- 저장 자료 변경 전후를 비교하고 예상 밖 분류 변경을 검토한다. 원문을 결과에 맞춰 수정하지 않는다.
- 실행 서버의 정책 버전·개별 주문 분류·확신도·화면 표시를 확인한 뒤 완료를 알린다.
- 수집 또는 발신 중인 서버를 재시작하지 않는다.
